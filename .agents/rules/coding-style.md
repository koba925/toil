Toilのソースコードは以下のコーディングスタイルに従います。

## 全般

Pythonの初心者でプログラミング言語処理系を初めて作る人にもわかりやすいコードを心がけてください。

# 詳細ルール

基本的にはPEP-8に従います。ただし、以下は例外とします。

* 行の長さは88文字までとします。ただしテストコードではこだわりません。
* ひとまとまりの意味を持つ複数の文を1行で書くことがあります。画面にできるだけ多くの情報を入れ、見通しをよくするためです。
* トップレベルの定義の間は基本的に２行空けますが、ごく短い定義はまとまり具合によって1行のみ、または行を空けずに続けて書くことがあります。
* 継承関係を無視して厳密に型を判定したいときはtype()を使います。
* importしたシンボルの有効範囲を狭めるため、importを先頭に置かないことがあります。
* 書籍で説明する予定であることと、コードを短く見通しよくしたいことからコードにはコメントを入れません。
  * コメントを入れなくても読みやすいコードになるよう心がけてください。
  * ただし、変数名や関数名は長すぎないようにします。
* 引用符はダブルクォーテーションを使います。
  * toilのソースコードは` r""" """ `で囲んで記述します（toilのソースコードに引用符を使うようになることを見越して）。
* 式を表す変数には_expr、値を表す変数には_valをつけます。そのため、argの値のリストを表す変数名はarg_valsではなく、args_valとなります。ただ値または式であることがわかればよい場合は単にvalまたはexprと書き、この場合は複数ならvals、exprsとなります。

## エラーチェック

* エラーチェックは最小限とします。Pythonのエラーで止まっても何が起きたかわかれば問題ないものとします。
* エラーはassertで上げます。エラーメッセージは f"{メッセージ} @ {関数}() : {エラーとなった値}"とします。
* エラーチェックをつける代表的なケースは以下の通りです。
  * matchで適切なcaseがなかった場合。
  * 再帰の基底ケースとしてのチェック。
  * 型をチェックしないと警告が出る場合。

## 実行例

* toil.pyのメインセクションの `# Example` コメント以下に実行例を置きます。これは Toil のコードの例示と、実装した機能のテストを兼ねます。
* エラーになる実行例はコメントアウトして書きます。
* できるだけ `eval()`、`walk()` または `run()` などを使って end-to-end で動作例を示したり、実行結果を確認できるようにします。
* `eval()`、`walk()` または `run()` などでは十分に動作を例示・説明しづらい場合は `scan()`、`ast()`、`compile()` などで途中結果を示すことも検討します。
* 0や1はFalse・Trueやその他の特別な値と混乱する場合があるため、実行例やテストで使う数は2から始めます。
* `<` などが正しく動作することについては Python を信用することにして網羅的にはテストしません。正しくPythonの機能が呼び出せていることが確認できればよいものとします。
* Toilが自分でエラーチェックをしている個所以外のエラー（引数の数、0除算など）はテストしなくても構いません。

## テスト

* テストメソッドは処理系のソースコードに現れる位置と対応付けやすいように並べます。
  （書籍では基本的に実行例を見せて説明する方針なので、テストは動作確認のしやすさに重点を置きます）
* テストのコードは実行例に準じます。
* テストにするのは `eval()`、`walk()` または `run()` の実行例のみとし、`scan()` や `ast()`、`compile()` などの実行例が存在してもテストに入れません。これはテストが内部構造に依存しないようにするためです。ただし、`walk()` または `run()` だけではテストが不十分と考えられる場合は追加を検討します。
* コメントになっているエラーの行があればそれらもテスト化します。
